# CodexBot

[English documentation](README.en.md)

CodexBot یک نرم‌افزار دسکتاپ محلی مبتنی بر PySide6 برای معاملات قراردادهای دائمی USDT-M در صرافی Bitunix است که ایمنی را در اولویت قرار می‌دهد. این برنامه از چند پروفایل استراتژی، بک‌تست واقع‌گرایانه، معامله آزمایشی (`PAPER`) با داده واقعی بازار و اجرای زنده‌ای که عمداً پشت چند مرحله تأیید قرار گرفته پشتیبانی می‌کند. CodexBot **هیچ تضمینی برای سودآوری نمی‌دهد**.

> [!WARNING]
> این نرم‌افزار معاملاتی آزمایشی است و توصیه مالی محسوب نمی‌شود. کار را با حالت `PAPER` شروع کنید، کد منبع را بررسی کنید و هر استراتژی را شخصاً اعتبارسنجی کنید. معامله زنده می‌تواند باعث از دست رفتن پول واقعی شود.

## امکانات

- داشبورد دسکتاپ، نمودار شمعی، تنظیمات استراتژی، گزارش‌ها و خروجی CSV معاملات.
- دریافت داده عمومی بازار Bitunix بدون نیاز به API key.
- بک‌تست قطعی چندبازه‌زمانی با لحاظ کارمزد، لغزش قیمت، اهرم و هم‌ترازی بدون نگاه به آینده (no-lookahead).
- اجرای آزمایشی محلی که امکان فراخوانی endpoint سفارش زنده را ندارد.
- اجرای زنده Bitunix با بررسی‌های اولیه حساب، حفاظت بومی صرافی و تأییدهای صریح.
- شش پروفایل پژوهشی/تشخیصی استراتژی، از جمله SP2L و اجرای Grid محدودشده.
- تست‌های خودکار برای رفتار استراتژی، ریسک، صرافی، بک‌تست، رابط گرافیکی و ذخیره‌سازی.

## راه‌اندازی سریع

> [!IMPORTANT]
> برای شروع، فقط از حالت `PAPER` استفاده کنید. بک‌تست و معامله آزمایشی به API key نیاز ندارند. هیچ کلید API را در چت، پیام، اسکرین‌شات یا مخزن Git قرار ندهید و تا زمانی که کد و تنظیمات حساب را شخصاً بررسی نکرده‌اید، حالت `LIVE` را فعال نکنید.

### روش اول: راه‌اندازی با کمک Codex یا Claude Code

ابتدا مخزن را clone کنید یا فایل ZIP را دانلود و استخراج کنید. سپس PowerShell را در پوشه پروژه باز کنید و یکی از ابزارهای `codex` یا `claude` را اجرا کنید. راهنمای رسمی نصب و شروع این ابزارها در [Codex CLI](https://developers.openai.com/codex/cli/) و [Claude Code](https://code.claude.com/docs/en/getting-started) در دسترس است.

اگر مخزن را با Git دریافت می‌کنید:

```powershell
git clone https://github.com/erfanrhb/CodexBot.git
Set-Location CodexBot
```

سپس یکی از این دو ابزار را در همان پوشه اجرا کنید:

```powershell
codex
# یا
claude
```

متن زیر را عیناً برای عامل کدنویسی بفرستید:

```text
این پروژه CodexBot را فقط برای استفاده امن در حالت PAPER راه‌اندازی کن. ابتدا وجود Python 3.11 یا جدیدتر را بررسی کن، سپس داخل همین پوشه یک محیط مجازی .venv بساز، آن را فعال کن، پروژه را همراه ابزارهای توسعه نصب کن، همه تست‌ها را اجرا کن و فقط در صورت موفق بودن مراحل برنامه را با python main.py اجرا کن. هیچ API key یا secret از من درخواست نکن، هیچ credential را ذخیره یا نمایش نده، فایل .env نساز مگر اینکه من بعداً صریحاً برای اتصال احراز هویت‌شده درخواست کنم، و به هیچ وجه حالت LIVE یا سفارش واقعی را فعال نکن. اگر خطایی رخ داد، علت و فرمان امن پیشنهادی را توضیح بده.
```

عامل باید نسخه Python را بررسی کند، `.venv` بسازد، `python -m pip install -e ".[dev]"` و `python -m pytest` را اجرا کند و در پایان برنامه را در حالت پیش‌فرض `PAPER` باز کند. پیش از اجرای هر فرمان پیشنهادی، آن را مرور کنید.

### روش دوم: راه‌اندازی دستی با PowerShell

در پوشه استخراج‌شده یا cloneشده پروژه اجرا کنید:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e "."
python main.py
```

برای نصب ابزارهای تست نیز، به‌جای فرمان نصب بالا اجرا کنید:

```powershell
python -m pip install -e ".[dev]"
python -m pytest
```

ساخت فایل `.env` برای بک‌تست و حالت `PAPER` لازم نیست. فقط اگر بعداً قصد تست اتصال احراز هویت‌شده یا استفاده آگاهانه از حالت زنده را داشتید، آن را به‌صورت محلی بسازید:

```powershell
Copy-Item .env.example .env
```

## استراتژی‌ها

انتخاب‌گر استراتژی میان بک‌تست، معامله آزمایشی و ارزیابی زنده مشترک است. هر پروفایل بازه‌های زمانی لازم و پیش‌فرض‌های پژوهشی خود را به‌طور خودکار اعمال می‌کند:

- **TestStrategy** — یک پروفایل صرفاً تشخیصی در بازه‌های 1m/5m که به‌شکل قطعی جهت انتخاب‌شده LONG یا SHORT را تولید می‌کند و در هر بار اجرای ربات به یک درخواست سفارش بازارِ محافظت‌شده محدود است. انتخاب آن در Live یک هشدار صریح درباره سفارش فوری اضافه می‌کند. این یک استراتژی کسب مزیت معاملاتی نیست و ادعایی درباره سودآوری ندارد.
- **GridStrategy** — یک Grid آزمایشی و محدودشده trend-pullback در بازه‌های 15m/4h. این استراتژی به رژیم و شیب EMA50/EMA200 روی کندل کامل‌شده 4H، فاصله 1 تا 3 درصدی EMAها، ATR قابل قبول، حجم بالاتر از میانه و گذار RSI به یک pullback نیاز دارد. دو سفارش limit هم‌وزن با فاصله یک ATR قرار می‌گیرند و از اندازه‌گذاری مارتینگل استفاده نمی‌شود. یک stop سخت از کل Grid محافظت می‌کند، targetها حداقل 2R را حتی از کم‌عمق‌ترین fill ممکن حفظ می‌کنند، سفارش‌های پرنشده پس از شش کندل منقضی می‌شوند و طرح‌های fillشده پس از بیست‌وچهار کندل timeout می‌شوند.
- **EMA Trend Pullback** — خط پایه long-short اولیه در بازه‌های 15m/1h.
- **SP2L (Poursamadi Spike-2Leg)** — پیاده‌سازی علّی price-action در بازه‌های 1m/5m که یک spike شکست 3 تا 9 کندلی را شناسایی می‌کند، وجود pressure gap را الزامی می‌داند، price action نامرتب پیش از spike را رد می‌کند و فقط پس از بسته‌شدن اولین کندل pullback، سفارش‌های limit پله‌ای را آماده می‌کند. پیش‌فرض، ورود دولایه‌ای مستندشده عمومی است؛ لایه سوم تهاجمی 4x تنها در صورت فعال‌سازی صریح استفاده می‌شود.
- **Vibe 4H / Daily Breakout** — استراتژی منتقل‌شده long-only شکست 4H که توسط رژیم EMA50/RSI یک کندل کامل‌شده روزانه محدود می‌شود. بازپخش CodexBot روی داده موجود VibeCode از 2025-01-01 تا 2026-08-27، با ریسک 0.5% و لحاظ کارمزد و لغزش قیمت، بازده +4.84%، ضریب سود 1.48 و حداکثر افت سرمایه 3.30% داشت. این نتیجه همچنان نمونه پژوهشی کوچک 33 معامله‌ای است و اثبات‌کننده مزیت آینده نیست.
- **Vibe 4H Candle Confirmation (Market)** — نسخه ورود بازار 15m/4h از استراتژی maker در VibeCode. عملکرد قدیمی maker-fill نباید به این نسخه نسبت داده شود: بازپخش بازار CodexBot منفی بود؛ بنابراین این پروفایل آزمایشی است و پیش از هرگونه بررسی برای اجرای زنده به اعتبارسنجی تازه نیاز دارد.

برنامه به‌جای اجرای خاموش یک پروفایل روی داده‌ای که برای آن طراحی نشده، ناسازگاری استراتژی و بازه زمانی را رد می‌کند.

### سابقه اعتبارسنجی GridStrategy

پیش‌فرض نهایی از یک جست‌وجوی کوچک و محدود روی تعداد لایه‌ها، فاصله ATR، حاشیه stop و time stop، با استفاده از داده BTCUSDT بین 2026-05-01 و 2026-06-30 انتخاب شد. کارمزد هر fill برابر 0.06%، لغزش قیمت 0.03%، ریسک 0.5%، اهرم 2x و الزام 2R ثابت بود. بخش آموزش BTC بازده +4.84% (PF برابر 7.17 و پنج رکورد خروج جزئی) داشت؛ holdout دست‌نخورده از 2026-07-01 تا 2026-08-30 فقط شامل یک طرح زیان‌ده بود و بازده -1.43% داشت. پنجره ترکیبی BTC بازده +3.34%، PF برابر 2.46 و حداکثر افت سرمایه 1.52% داشت. همین پیش‌فرض‌ها روی ETHUSDT در پنجره ترکیبی بازده +3.83%، PF برابر 2.51 و حداکثر افت سرمایه 3.45% داشتند؛ بخش ابتدایی آن -1.44% و holdout بعدی +5.34% بود. این نمونه‌ها کوچک و نتایج آن‌ها ترکیبی هستند. صرفاً یک پروفایل آزمایشی برای بک‌تست/معامله آزمایشی را توجیه می‌کنند و وعده سودآوری زنده نیستند.

### قواعد اجرای SP2L

- spikeهای صعودی به lowهای متوالیِ غیرکاهشی و spikeهای نزولی به highهای متوالیِ غیر‌افزایشی نیاز دارند. spike طولانی‌تر از 9 کندل به‌عنوان فرسودگی احتمالی رد می‌شود.
- کندل اول یا دوم spike باید با بسته‌شدنی قدرتمند از محدوده ثابت قبلی عبور کند و کندل follow-through باید نسبت به کندل پیش از شکست یک pressure gap ایجاد کند.
- پروفایل بهینه‌شده BTCUSDT کل نشست روزهای کاری هفته را بررسی و shortها را با رژیم آخرین EMA60 کامل‌شده 15m هم‌راستا می‌کند. فیلتر نشست محدود به لندن/نیویورک و حالت هر دو جهت برای ابزارهای دیگر و پژوهش همچنان در دسترس‌اند.
- اولین نقض سخت low/high محرک pullback است. چون ربات فقط از کندل‌های بسته‌شده استفاده می‌کند، محرک سفارش‌های limit را برای کندل‌های بعدی آماده می‌کند و هرگز مدعی fill غیرقابل‌تشخیص درون کندل محرک نمی‌شود.
- Entry 1، low/high کندل قبلی را دوباره آزمایش می‌کند. پروفایل بهینه‌شده BTCUSDT، Entry 2 را روی EMA60 قرار می‌دهد؛ حالت‌های midpoint-to-stop و spike-midpoint همچنان قابل تنظیم‌اند. Entry 3 از وزن 4x در نزدیکی stop استفاده می‌کند، اما انتخابی است.
- stopها می‌توانند از مبدأ spike (پیش‌فرض)، کندل follow-through یا سطح 50% spike استفاده کنند. پروفایل بهینه‌شده 70% را در 1R می‌بندد؛ TP2 مقدار دورتر میان measured move و حداقل 2R الزامی سیستم را به کار می‌گیرد. limitهای پرنشده پس از پنج کندل منقضی می‌شوند و معاملات باز پس از سی کندل timeout می‌شوند.
- بک‌تستر همه لایه‌ها، TP1 جزئی، TP2، stop، انقضای limit، کارمزدها، اهرم و time stop را مدل می‌کند. حالت Paper، limitهای معلق واقعیِ محلی می‌سازد و مقدار هر لایه را بین TP1/TP2 تقسیم می‌کند. حالت Live همان بخش‌ها را به‌شکل سفارش‌های GTC limit رهگیری‌شده با client IDهای یکتا و triggerهای market SL/TP بومی صرافی ثبت می‌کند.

روش منبع، طلا، شاخص‌ها و فارکس را شرح می‌دهد؛ اما adapter فعلی صرافی در این مخزن فقط از نمادهای قرارداد دائمی USDT در Bitunix پشتیبانی می‌کند. XAUUSD و US30 به broker/data adapter جداگانه نیاز دارند؛ خود منطق استراتژی مستقل از دارایی است.

منابع عمومی روش: [مرور SP2L محمدعلی پورصمدی](https://poursamadi.com/en/sp2l-strategy-spike-2leg-by-mohammad-ali-poursamadi/) و [توضیحات اندیکاتور SP2L در TradingFinder](https://www.tradingview.com/script/Qiv9aTi0-SP2L-Pour-Samadi-Indicator-TradingFinder-Spike-2-Legs-PA/).

### سابقه بهینه‌سازی SP2L

پیش‌فرض‌های BTCUSDT 5m از یک جست‌وجوی گسترده قطعی با 1,024 آزمون و سپس یک جست‌وجوی همسایگی با 768 آزمون روی بازه 2026-05-30 تا 2026-08-30 انتخاب شدند. توسعه از سه fold زمانی تا 2026-08-01 استفاده کرد؛ بازه 2026-08-01 تا 2026-08-30 تا زمان اعتبارسنجی finalist کنار گذاشته شد. ریسک روی 0.5%، کارمزد هر fill روی 0.06% و لغزش نامطلوب روی 0.03% ثابت ماند و الزامات ایمنی gap/2R هرگز از بهینه‌سازی حذف نشدند. پروفایل نهایی در کل نمونه بازده +4.02%، ضریب سود 3.00، حداکثر افت سرمایه 0.88% و 35 خروج ثبت‌شده داشت؛ holdout دست‌نخورده بازده +0.46%، ضریب سود 1.79 و 13 خروج داشت. این‌ها نمونه‌های تاریخی کوچک هستند، نه تضمین سودآوری. پیش از استفاده زنده، روی داده جدیدتر دوباره اعتبارسنجی کنید. آزمون فشار هزینه اجرا در کارمزد 0.08% به‌علاوه لغزش 0.05% همچنان مثبت بود (+2.54%، PF برابر 1.98) و در کارمزد 0.10% به‌علاوه لغزش 0.07% نیز مثبت ماند (+1.08%، PF برابر 1.33)، اما در کارمزد 0.15% به‌علاوه لغزش 0.10% شکست خورد (-2.02%). بنابراین این پروفایل به هزینه حساس است.

بهینه‌ساز قابل بازتولید در `scripts/optimize_sp2l.py` قرار دارد و نتایج تفصیلی جست‌وجوی گسترده و متمرکز در `optimization/` ذخیره شده‌اند.

### بررسی برابری VibeCode

استراتژی Vibe 4H / Daily Breakout در هر دو موتور روی فایل‌های یکسان Bitunix و پنجره 2025-01-01 تا 2026-08-27 بازپخش شد؛ با سرمایه آغازین $10,000، ریسک 0.5%، اهرم 1x، کارمزد هر fill برابر 0.06%، لغزش 0.03%، ATR برابر 2.0، نسبت R:R برابر 2:1 و فیلتر آخر هفته غیرفعال. نتایج تا دقت ممیز شناور یکسان‌اند:

| موتور | بازده | ضریب سود | معاملات | حداکثر افت سرمایه |
|---|---:|---:|---:|---:|
| VibeCode | 4.8224256522% | 1.4827427242 | 33 | 3.1850462636% |
| CodexBot | 4.8224256522% | 1.4827427242 | 33 | 3.1850462636% |

CodexBot برای پیروی از سیاست معاملاتی سیستم، مسدودسازی آخر هفته را به‌صورت پیش‌فرض فعال نگه می‌دارد. با فعال بودن این سیاست روی همان نمونه، CodexBot تعداد 30 معامله، بازده +4.96%، ضریب سود 1.56 و حداکثر افت سرمایه 2.86% داشت. این نتیجه تعدیل‌شده بر اساس سیاست است، نه اجرای برابری دقیق VibeCode.

زبانه Backtest اهرم و فیلتر آخر هفته را نمایش می‌دهد. انتخاب استراتژی، preset پژوهشی ریسک، اهرم، کارمزد، لغزش، ATR، R:R و بازه زمانی آن را بارگذاری می‌کند؛ مسدودسازی آخر هفته همچنان یک انتخاب صریح و قابل مشاهده است.

## مدل ایمنی

- حالت پیش‌فرض `PAPER` است.
- سفارش‌های Paper فقط توسط `PaperExchange` اجرا می‌شوند و هرگز endpoint سفارش Bitunix را فراخوانی نمی‌کنند.
- ریسک هر معامله حداکثر 1% است و reward/risk تنظیم‌شده نمی‌تواند کمتر از 2:1 باشد؛ مطابق سیاست معاملاتی سیستم.
- ورود در آخر هفته به‌طور پیش‌فرض مسدود است. پیش از پنجره‌های CPI/FOMC گزینه **Macro Event Blackout** را روشن کنید؛ برنامه تقویم اقتصادی را حدس نمی‌زند.
- حالت Live به credentialهای موجود در متغیرهای محیطی، تست اتصال احراز هویت‌شده موفق، انتخاب `LIVE`، یک کادر هشدار و تأیید متنی `yes` نیاز دارد.
- اجرای زنده SP2L، limitهای GTC پله‌ای و مقدارهای جداگانه TP1/TP2 را حفظ می‌کند؛ ثبت ناقص سفارش‌ها rollback می‌شود و طرح به سفارش بازار تنزل پیدا نمی‌کند.
- GridStrategy از همان موتور GTC limit رهگیری‌شده و rollback-safe با client IDهای `cbgrid` استفاده می‌کند. مقدار کل طرح یک‌بار بر اساس ریسک اندازه‌گذاری، به‌طور مساوی تقسیم و رو به پایین گرد می‌شود تا دقت لایه‌ها exposure درخواستی را افزایش ندهد.
- اجرای زنده از position mode نوع `ONE_WAY` در Bitunix پشتیبانی می‌کند. اگر حساب در حالت `HEDGE` باشد، برنامه ابتدا همه نمادهای futures را بررسی می‌کند، با تأیید متنی `yes` فقط سفارش‌های قدیمی متعلق به CodexBot را برای لغو پیشنهاد می‌دهد، از کاربر می‌خواهد سفارش‌ها و positionهای خارجی را پاک کند، پس از دومین `yes` متنی حالت سراسری حساب را تغییر می‌دهد و نتیجه را تأیید می‌کند.
- هنگام شروع Live، برنامه اهرم و margin mode فعلی نماد انتخاب‌شده را می‌خواند. فقط مقادیر ناسازگار را پس از تأیید صریح تغییر می‌دهد و هر دو را از طریق endpoint خواندن Bitunix تأیید می‌کند.
- توقف Live در صورت باقی‌ماندن سفارش‌های entry متعلق به CodexBot تأیید متنی می‌خواهد، فقط همان سفارش‌ها را لغو می‌کند و تا زمانی که Bitunix عدم pending بودن آن‌ها را تأیید کند polling انجام می‌دهد. positionهای موجود صرافی هرگز بی‌اطلاع بسته نمی‌شوند.
- موجودی حساب Live، PnL تحقق‌نیافته، positionها و سفارش‌های pending از پاسخ‌های REST احراز هویت‌شده Bitunix cache می‌شوند؛ Dashboard در حالت Live هرگز مقادیر کیف پول Paper را جایگزین نمی‌کند.
- سلامت WebSocket عمومی داده بازار و WebSocket خصوصی سفارش/position جداگانه رهگیری و نمایش داده می‌شود.
- credentialها فقط از `BITUNIX_API_KEY` و `BITUNIX_API_SECRET` بارگذاری می‌شوند. هرگز ذخیره پایدار یا در log نمایش داده نمی‌شوند.
- هیچ قابلیت برداشت وجهی وجود ندارد.

از API keyای استفاده کنید که فقط مجوزهای ضروری معاملات futures را دارد. مجوز برداشت نه لازم است و نه توصیه می‌شود.

## گردش کار رابط گرافیکی

### بک‌تست

1. زبانه **Backtest** را باز کنید.
2. نماد، استراتژی، محدوده تاریخ، موجودی آغازین، بازه‌های زمانی بالاتر/ورود، کارمزد، لغزش، ریسک، risk/reward و ضریب ATR را انتخاب کنید.
3. **RUN BACKTEST** را بزنید. دریافت داده و محاسبه روی Qt worker thread اجرا می‌شوند تا پنجره پاسخ‌گو بماند.
4. آمار، منحنی equity و تاریخچه معاملات را بررسی کنید. با **EXPORT TRADES CSV** معاملات را ذخیره کنید.
5. دکمه **CANCEL** میان مراحل پردازش درخواست لغو قطعی می‌دهد.

داده تاریخی Bitunix در `cache/` ذخیره موقت می‌شود. فقط کندل‌های کامل‌شده پذیرفته می‌شوند. داده مرتب و از نظر timestamp تکراری، مقادیر OHLC نامعتبر و سازگاری بازه زمانی بررسی می‌شود. feed رسمی گاهی `high`/`low`ای برگردانده که به‌اندازه یک tick داخل محدوده open/close خودش بوده است؛ adapter Bitunix فقط همان envelope را پیش از اعتبارسنجی سخت clamp می‌کند.

### معامله آزمایشی (Paper)

1. زبانه **Paper / Live** را باز کنید و حالت را روی `PAPER` نگه دارید.
2. **START BOT** را بزنید.
3. موتور به‌روزرسانی‌های ticker/candle فعلی را از WebSocket عمومی Bitunix دریافت می‌کند، فقط کندل‌های بسته‌شده را برای سیگنال بارگذاری می‌کند، اعتبارسنجی ریسک با توجه به precision انجام می‌دهد و سفارش‌های شبیه‌سازی‌شده محلی می‌سازد. اگر stream قدیمی شود، REST polling محدودشده مسیر بازیابی است.
4. کارمزد، لغزش نامطلوب، رزرو margin مبتنی بر اهرم، اندازه position محدودشده بر اساس توان مالی، SL و TP مدل می‌شوند.
5. برای جلوگیری از سیگنال‌های جدید **STOP BOT** را بزنید. positionهای Paper موجود همچنان به‌صورت محلی نمایش داده می‌شوند.

### معامله زنده (Live)

1. ابتدا استراتژی، ریسک، اهرم، margin mode و نماد را تنظیم کنید.
2. credentialها را در محیط محلی بگذارید و از **Exchange → TEST CONNECTION** استفاده کنید.
3. `LIVE` و سپس **START BOT** را انتخاب کنید.
4. هشدار را بخوانید و `yes` تایپ کنید.
5. بررسی اولیه Live وجود position و سفارش pending خارجی را رد می‌کند. اگر سفارش‌های قدیمی `cb*` از نشست قبلی CodexBot پیدا شود، برای لغو و تأیید فقط همان سفارش‌ها `yes` تایپ کنید.
6. اگر حساب در حالت `HEDGE` است، هشدار سراسری حساب را بخوانید و برای اجازه درخواست و تأیید حالت `ONE_WAY` توسط CodexBot، `yes` تایپ کنید.
7. اگر اهرم یا margin mode متفاوت است، مقادیر قبل/بعد را مرور کنید و برای تغییر و تأیید فقط نماد انتخاب‌شده `yes` تایپ کنید.
8. موتور پیش از فعال‌سازی اجرا، positionها، سفارش‌های pending، `ONE_WAY`، اهرم، margin mode و precision ابزار را دوباره بررسی می‌کند. سفارش‌های SP2L تا fill یا انقضا به‌صورت resting می‌مانند و حفاظت SL/TP بومی صرافی را حفظ می‌کنند.
9. هنگام توقف Live، در صورت درخواست برای لغو و تأیید entryهای pending متعلق به CodexBot، `yes` تایپ کنید. positionهای موجود با حفاظت صرافی باز می‌مانند.

ثبت سفارش زنده، شامل جهت بازار، مقدار base-coin، `reduceOnly` و فیلدهای market SL/TP بومی صرافی با `LAST_PRICE` پیاده‌سازی شده است. این قابلیت در زمان توسعه **روی حساب دارای موجودی اجرا نشده است**. تا زمانی که کد را بررسی و آن را با API key محدودشده و تنظیمات حساب خود اعتبارسنجی نکرده‌اید، از حالت Live استفاده نکنید.

### سفارش آزمایشی واقعی API

زبانه **Exchange** شامل **TEST ORDER** برای بررسی کامل مسیر سفارش احراز هویت‌شده بدون اجرای ربات است. نماد دقیق futures، جهت، اندازه سفارش بر حسب ارزش اسمی USDT، limit entry، stop loss، take profit و اهرم را وارد کنید. CodexBot اندازه USDT را با قیمت limit واردشده به مقدار base-coin مورد نیاز Bitunix تبدیل و آن را مطابق precision صرافی رو به پایین گرد می‌کند. برنامه به ربات idle، credentialهای احراز هویت‌شده، نبود position/order متعارض، position mode نوع `ONE_WAY`، precision معتبر Bitunix، حداقل reward/risk برابر 2:1 و ریسک تخمینی stop حداکثر 1% equity حساب نیاز دارد.

پس از مرور خلاصه پول واقعی و تایپ `yes`، CodexBot فقط در صورت نیاز تغییر اهرم را اعمال و تأیید می‌کند، یک سفارش limit واقعی محافظت‌شده ثبت می‌کند، وضعیت معتبر آن را از Bitunix می‌خواند و باقی‌مانده پرنشده را فوراً لغو و نتیجه را تأیید می‌کند. Bitunix برای این گردش کار endpoint آزمایشی ندارد. یک limit قابل معامله ممکن است پیش از لغو fill شود؛ پنل نتیجه order ID و مقدار fillشده را گزارش می‌کند و CodexBot هرگز position واقعی حاصل را بی‌اطلاع نمی‌بندد.

کلاینت‌های WebSocket عمومی و خصوصی heartbeatهای کاربردی Bitunix را در deadline ثابت حتی هنگام ترافیک پیوسته بازار ارسال می‌کنند. قطع غیرمنتظره transport همچنان باعث reconnection خودکار محدودشده می‌شود؛ وضعیت بعدی `CONNECTED` بازیابی را تأیید می‌کند.

## قواعد اجرای بک‌تست

- timestamp کندل‌ها نشان‌دهنده زمان بازشدن کندل است. زمان بسته‌شدن از timeframe محاسبه می‌شود.
- سیگنال محاسبه‌شده در بسته‌شدن کندل N، با لغزش نامطلوب قابل تنظیم در بازشدن کندل N+1 اجرا می‌شود.
- مقادیر timeframe بالاتر فقط پس از کامل‌شدن کندل همان timeframe قابل مشاهده‌اند. هم‌ترازی از backward as-of matching روی زمان‌های بسته‌شدن محاسبه‌شده استفاده می‌کند.
- مقدار position بر اساس درصد تنظیم‌شده حساب از entry تا ATR stop ریسک‌گذاری می‌شود، توسط margin در دسترس مبتنی بر اهرم به‌علاوه کارمزد entry محدود می‌شود و مطابق precision پایه صرافی رو به پایین گرد می‌شود.
- قیمت‌ها مطابق quote precision صرافی گرد می‌شوند. حداقل مقدار و حداکثر مقدار بازار از metadata ابزار Bitunix می‌آیند؛ اگر صرافی minimum notional ارائه کند، آن نیز بررسی می‌شود.
- کارمزد entry و exit جداگانه محاسبه می‌شوند.
- اگر SL و TP هر دو در یک کندل OHLC باشند و ترتیب tick در دسترس نباشد، SL برنده است. این رفتار برای معاملات long و short قطعی و محافظه‌کارانه است.
- position باز در انتهای داده با قیمت close نهایی، لغزش نامطلوب و کارمزد بسته می‌شود.

## معماری

```text
PySide6 GUI
  -> ApplicationController / services
    -> TradingService or BacktestService
      -> selected strategy from registry + RiskManager
        -> PaperExchange or BitunixClient
```

GUI هیچ محاسبه‌ای برای signing صرافی، استراتژی، sizing یا بک‌تست ندارد. سرویس معامله بدون GUI نیز کار می‌کند. stateهای صریح `STOPPED`، `CONNECTING`، `RUNNING_BACKTEST`، `RUNNING_PAPER`، `RUNNING_LIVE` و `ERROR` از عملیات متعارض و شروع‌های تکراری جلوگیری می‌کنند.

```text
app/             application controller
backtesting/     sequential simulator and metrics
config/          validated settings and persistence
data/            historical download, cache, validation
engine/          application state machine
execution/       exchange abstraction, Bitunix REST/WS, paper exchange
gui/             PySide6 views, chart, worker
indicators/      EMA, RSI, ATR
models/          orders, signals, positions, trades, results
risk/            position sizing, stops, targets, precision
services/        backtest and independent trading services
strategies/      registry, EMA baseline, 4H/daily breakout, and 4H confirmation
tests/           deterministic automated tests
utils/           logging integration
scripts/         safe integration smoke checks
main.py          desktop entry point
```

موارد تأییدشده در زمان توسعه:

- هر 76 تست خودکار پاس می‌شوند؛
- GUI در یک smoke test آفلاین Qt با موفقیت ساخته و بسته می‌شود؛

- فراخوانی‌های REST عمومی metadata ابزار، ticker و kline تاریخی کار می‌کنند؛
- یک بک‌تست integration واقعی عمومی 14روزه BTCUSDT روی بیش از 1,300 کندل ورود کامل شد؛ ورودهای آخر هفته طبق سیاست حذف شدند؛
- اشتراک ticker در WebSocket عمومی Bitunix داده دریافت می‌کند؛
- خواندن احراز هویت‌شده حساب Bitunix، position، سفارش pending، اهرم و margin mode کار می‌کند؛
- login در WebSocket خصوصی Bitunix و subscription سفارش/position با credentialهای محدودشده تنظیم‌شده کامل می‌شود؛
- حالت Paper داده جاری WebSocket بازار را مصرف کرد و چون اعتبارسنجی در روز یکشنبه انجام شد، سیگنال را طبق قاعده نقدشوندگی آخر هفته به‌درستی رد کرد؛ تست‌های قطعی اجرای محلی `paper-*` را بدون رسیدن به adapter زنده تأیید می‌کنند.

- ثبت سفارش زنده، reconciliation شدن fill، لغو یا رفتار حساب دارای موجودی؛

## رفع اشکال

- **پیغام `python` is not recognized:** Python 3.11+ را از python.org نصب و گزینه افزودن Python به `PATH` را در installer فعال کنید.
- **خطای platform/plugin در Qt:** محیط مجازی پروژه را فعال و با `python -m pip install --force-reinstall PySide6` دوباره نصب کنید.
- **نبود داده بازار:** اتصال اینترنت و دسترسی Bitunix از شبکه خود را بررسی کنید. کندل‌های cacheشده همراه release توزیع نمی‌شوند.
- **شکست احراز هویت Live:** نام دو متغیر `.env` را دقیقاً بررسی کنید، پس از تغییر آن‌ها برنامه را دوباره اجرا کنید و مطمئن شوید API key مجوزهای futures لازم را دارد. مجوز برداشت لازم نیست.
- **رد بازه‌های زمانی انتخابی توسط استراتژی:** استراتژی را دوباره انتخاب کنید تا preset ثابت timeframe آن اعمال شود.

## حریم خصوصی و امنیت

آرشیوهای release و commitهای Git نباید شامل `.env`، `config.json`، cacheها، exportها، logها، خروجی coverage، تنظیمات IDE یا artifactهای build پایتون باشند. فایل `.env.example` موجود فقط placeholderهای خالی دارد. اگر credentialها زمانی commit شده باشند، حذف فایل کافی نیست—کلیدها را تعویض و آن‌ها را پیش از انتشار از تاریخچه Git پاک کنید.
